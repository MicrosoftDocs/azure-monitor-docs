# Data collection in Azure Monitor

Azure Monitor collects telemetry from Azure resources, applications, operating systems, Kubernetes clusters, custom clients, and hybrid or multicloud environments. Different sources and signals support different collection methods.

This article guides you through five planning steps:

1. Identify the collection paths supported for your source and signal.
1. Understand how collection affects cost.
1. Choose a topology for your operational needs.
1. Decide where to process data.
1. Understand storage and connected experiences.

For a source-by-source catalog, see [Azure Monitor data sources and data collection methods](../fundamentals/data-sources.md).

## 1. Identify supported collection paths

Azure Monitor provides three broad collection families:

- **Use platform-native collection** for telemetry generated by Azure resources and platform services. Some activity logs and platform metrics are collected automatically. For supported resources, use DCR-based [platform log collection (preview)](platform-logs-collect.md) and [metrics export](metrics-export-create.md) to collect and route platform telemetry.
- **Use direct collection** when an instrumented application, SDK, exporter, or API client sends data to an Azure Monitor cloud endpoint. Examples include [Application Insights](../app/app-insights-overview.md) and the [Logs ingestion API](../logs/logs-ingestion-api-overview.md).
- **Use collector-based collection** to collect more telemetry or introduce processing, resilience, and operational control before cloud ingestion.
  - [Azure Monitor agent](../agents/azure-monitor-agent-overview.md) runs on monitored machines to collect guest operating system and workload data. Enabling [Container insights and Azure Monitor managed service for Prometheus](../containers/kubernetes-monitoring-enable.md) on a Kubernetes cluster installs a containerized Azure Monitor agent.
  - [Azure Monitor pipeline](pipeline-overview.md) is a centralized collection tier that runs off the monitored resources. It fans in telemetry from many producers and provides centralized processing, governance, cost control, and persistent buffering.

:::image type="content" source="media/overview/collection-paths.svg" alt-text="Diagram comparing three collection paths that use a common cloud ingestion endpoint in Azure Monitor. These paths aren't mutually exclusive. For example, you can use platform-native collection for an Azure resource, Application Insights for its application, and Azure Monitor agent for its guest operating system.

## 2. Understand collection costs

There's no separate Azure Monitor usage charge for Azure Monitor agent or Azure Monitor pipeline. Azure Monitor charges are based on the data uploaded to the cloud and the ingestion, retention, or storage pricing for its destination. Azure Monitor cloud ingestion and storage volume exclude data that Azure Monitor agent or Azure Monitor pipeline filters out before upload.

You remain responsible for costs outside the Azure Monitor collection service. Depending on your topology, these costs can include compute for an Arc-enabled Kubernetes cluster, persistent storage configured for Azure Monitor pipeline, and network transfer or egress charges.

For pricing and optimization guidance, see [Azure Monitor Logs cost calculations and options](../logs/cost-logs.md) and [Cost optimization in Azure Monitor](../fundamentals/best-practices-cost.md).

## 3. Choose a topology for your operational needs

When your source supports multiple paths, choose based on the operational characteristics you need:

- Use **Azure Monitor agent** for collection and resilience on each monitored machine or Kubernetes cluster.
- Use **Azure Monitor pipeline** with any supported producer—not only sources that can't run an agent—when you need consistent governance, high-volume fan-in, preprocessing across producers, cost control, or persistent buffering through connectivity interruptions.
- Combine Azure Monitor agent and pipeline where supported when you need both collection close to resources and centralized processing.

The source category alone doesn't determine the topology. Protocol, signal, and preview support varies by method. See [What is Azure Monitor pipeline?](pipeline-overview.md) for its supported sources and capabilities.

## 4. Decide where to process data

[Data collection rules (DCRs)](data-collection-rule-overview.md) provide a common Azure control plane for collection, processing, and routing in supported scenarios. Method-specific configuration still applies. For example, you configure application instrumentation in the application, and Azure Monitor pipeline uses local dataflows before DCR-controlled delivery to Azure Monitor.

Processing can occur in the application or source, on Azure Monitor agent, in Azure Monitor pipeline, and during Azure Monitor cloud ingestion. Choose the stage based on your requirements:

- Process before cloud upload to reduce network traffic, ingestion volume, or exposure of data that shouldn't leave the environment.
- Process at cloud ingestion when the transformation needs the Azure Monitor schema or consistent cloud-side application.
- Retain raw data when you might need it for future analysis, reprocessing, audit, or troubleshooting. Filtering or aggregation before upload permanently removes that detail from the cloud destination.

You can combine processing stages. Cloud transformations complement source, agent, and pipeline processing, but they occur after data has already been uploaded.

> [!NOTE]
> **Multi-stage transformations are in public preview.** A single DCR can coordinate client-side processing on Azure Monitor agent and ingestion-time processing in Azure Monitor. [Learn more about multi-stage transformations](data-collection-transformations.md#multi-stage-transformations-preview).

## 5. Understand storage and connected experiences

Depending on the signal and collection method, Azure Monitor stores collected data in either [Azure Monitor Logs](../logs/log-analytics-overview.md) or [Azure Monitor Metrics](../metrics/data-platform-metrics.md).

- **Microsoft Sentinel** provides security analytics over data in a Sentinel-enabled Log Analytics workspace.
- **Microsoft Fabric** can access Azure Monitor Logs through [Mirror Azure Monitor](../fundamentals/monitor-cross-domain-fabric.md). The data remains in Azure Monitor and is exposed in Fabric without being copied.
- Platform-native export scenarios can also use destinations such as Azure Storage or Event Hubs where supported.

Not every collection method supports every destination. Review the documentation for the selected method before finalizing your architecture.
